> **一句话重点：P1 先做“销售怎么说、正式材料怎么写”的双材料对照，再增加文件识别、证据追问和确定性计算；双产品 PK 最后做。**

| 项目 | 说明 |
|---|---|
| 执行分支 | 只使用 `main`，每次开工前记录 `git rev-parse HEAD` |
| 前置状态 | 团队确认 P0 已完成；开始 P1 前按第 1 节快速验收 |
| 技术方向 | Vue3 + Vant H5；Python + FastAPI 模块化单体 |
| 模型调用 | 后端统一一个 API Key；H5 不接触 Key 和供应商地址 |
| 项目边界 | Demo，不使用 Docker，不增加微服务、账号、服务端数据库或生产级中间件 |
| 执行方式 | Cursor 每次只处理一个 P1 编号，每项独立测试、验收和提交 |

# 第一部分：是否可以直接进入 P1

## 1. P0 快速验收门槛

开始 P1 前只检查下面六项，不重新做一轮 P0：

- [ ] H5 已能完成“输入文本 → 查看真实阶段 → 查看结构化报告 → 失败重试”。
- [ ] 模型超时、非法 JSON 或规则异常不会返回正常的空风险报告。
- [ ] API 输入输出使用 Pydantic；风险等级和状态不是自由文本。
- [ ] 每个关键结论有原文证据，或者明确显示“材料未说明/待确认”。
- [ ] 四组否定句回归样例通过，测试默认使用固定 Fixture/Mock，而不是依赖真实模型随机输出。
- [ ] API Key 只在 Python 后端配置，H5 不显示 Key 输入框和任意 `base_url`。

判断规则：

- 六项全部通过：继续 P1-01。
- 只有页面样式小问题：记录后继续，不阻塞 P1。
- 前四项任一不通过：先暂停补齐对应 P0，不能用 P1 功能掩盖旧问题。

# 第三部分：统一数据模型

## 3. P1 新增模型

不要把所有字段继续塞进一个越来越大的 `AnalysisReport`。P1 功能使用独立 Schema，通过 ID 和证据关联：

| 模型 | 关键字段 | Java 开发可类比为 |
|---|---|---|
| `SourceDocument` | `source_id`、`source_type`、`name`、`pages` | 文档聚合根 |
| `EvidenceRef` | `source_id`、页码、原文、位置、置信度、是否人工修改 | Evidence DTO |
| `ExtractedField[T]` | 原始值、标准值、单位、状态、证据 | 泛型字段值对象 |
| `Claim` | `claim_id`、主体、条件、动作、数值、否定状态、证据 | 标准化主张值对象 |
| `ClaimComparison` | 销售主张、正式材料事实、状态、双方证据 | 对照结果 DTO |
| `EvidenceAnswer` | 问题、回答状态、回答、证据、缺失信息 | 追问响应 DTO |
| `CalculationResult` | 公式、输入、假设、结果、舍入规则 | 计算结果值对象 |
| `ProductFacts` | `product_id`、固定字段、标准值、状态、证据 | 产品事实聚合根 |
| `ProductComparison` | 固定维度、A/B 值、差异状态、双方证据 | 产品对比 DTO |

统一枚举：

```text
SourceType = SALES_PITCH | OFFICIAL_DOCUMENT | USER_INPUT
ComparisonSide = A | B
FieldStatus = CONFIRMED | MISSING | CONFLICTING | UNCERTAIN
ClaimStatus = CONFIRMED | NOT_FOUND | CONFLICT | CONDITIONAL | UNCERTAIN
AnswerStatus = ANSWERED | INSUFFICIENT_EVIDENCE | OUT_OF_SCOPE
```

统一不变量：

- 没有 `EvidenceRef` 的金融结论不能显示为“已确认”。
- `NOT_FOUND` 表示当前材料未找到，不表示现实中不存在。
- OCR 没识别到与材料没写必须区分。
- 用户修改提取文本后，证据标记为 `user_corrected=true`。
- `ComparisonSide` 只表示界面上的 A/B 位置；材料归属使用 `subject_id/product_id`，不能与 `SourceType` 混为一个枚举。
- `Claim` 和 `ProductFacts` 使用稳定 ID；金额、比例、期限和单位必须先标准化，再进入对照或计算。
- 所有 P1 返回继续复用 P0 的 `TaskStatus`、`StageStatus` 和错误结构。

# 第四部分：各项详细实施

## P1-01 同一产品双材料对照

### 目标

让用户分别输入“销售话术”和“正式材料”，输出哪些内容一致、没写入、冲突、存在附加条件或无法判断。

### 用户流程

1. H5 选择“销售与材料对照”。
2. 输入 A：销售聊天、宣传话术或口头承诺整理。
3. 输入 B：产品说明、合同条款或风险揭示内容。
4. 系统先分别走 P0 分析链路，再生成对照结果。
5. 报告按重要性展示对照卡，每张卡可展开 A/B 两侧原文。

### 服务端处理

- 新增 `SourceDocument`、`ClaimComparison` 和 `ClaimStatus`。
- 新增 `AnalyzeDualSourcesUseCase`，但复用 P0 的分类、抽取、规则和证据校验。
- 先把 A 中承诺抽成结构化 Claim，再到 B 中找候选事实；数值、否定和单位由程序二次判断。
- `12 个月` 与 `1 年`、`0.5%` 与 `50bp` 标准化后再比较。
- 正式材料没写只能返回 `NOT_FOUND`，不能直接断言销售撒谎。

### H5 处理

- 两个输入区上下排列，不做桌面式左右双栏。
- 结果使用纵向卡片，状态文案为“一致、正式材料未找到、存在冲突、附加条件、待确认”。
- 每张卡展示一句话差异、销售原文、正式材料原文和建议追问。

### 测试样例

- A/B 含义和数值一致。
- A 承诺收益，B 完全未写。
- A 说“不收费”，B 说“收取 0.5%”。
- A 省略提前退出条件，B 存在附加条件。
- B 表述模糊，无法确定。

### 验收

- 五种 `ClaimStatus` 各有固定 Fixture。
- 每项结果至少引用一侧证据；冲突结果必须同时引用 A/B。
- 单边为空时不生成伪对照报告，而是提示补充材料。
- 不判断合同法律效力，不给销售人员打分。

### 建议文件

```text
backend-python/app/domain/rules/claim_matcher.py

frontend-h5/src/views/DualInputView.vue
```

## P1-02 PDF/图片输入与提取确认

### 目标

在保留纯文本输入的同时，支持手机相册、拍照、JPG、PNG 和单个 PDF，统一转换成带页码的 `SourceDocument`。

### Demo 限制

- 单个 PDF 不超过 10 页、10MB；图片最多 5 张。
- 只支持中文印刷体；暂不保证手写、复杂表格、公式、Word、Excel 和批量文件。
- 普通 PDF 优先提取已有文本层；某页没有可用文字时才调用 OCR。
- 普通 PDF 文本层使用一个轻量 PDF 提取 Adapter；OCR 默认复用当前后端同一 API Key 可调用的视觉模型，实现 `VisionOcrGateway`。
- 如果当前模型端点不支持图片输入，则明确返回 `OCR_UNAVAILABLE` 并延期扫描件 OCR，不临时增加第二个 Key、系统级 OCR 或多供应商平台。

### 服务端处理

- 定义 `DocumentParser` 和 `OcrGateway` Protocol。
- 处理图片旋转、页码、空白页、重复文本和局部失败。
- 每页返回 `success/failed`、文本、置信度和错误原因；部分页面失败时整体返回 `partial`。
- 临时文件分析结束后删除，不增加数据库和对象存储。
- OCR 使用固定 Mock 做自动测试；真实 OCR 只做手工冒烟，避免 CI 波动。

### H5 处理

- 上传前允许预览、删除和调整图片顺序。
- 提取后必须先展示可编辑文本；用户确认后才进入金融分析。
- 低置信度数字、费率和日期明显标记，支持逐项修正。
- 单页失败可以移除或重试，不必重新上传全部材料。

### 验收

- 文本 PDF、扫描 PDF、旋转图片、模糊百分比、多页顺序和空白页各有一个固定样例。
- `3.5%`、`1 万元`、`R1` 等敏感内容有人工确认入口。
- OCR 空文本不能当成成功，失败页不能生成“未发现风险”。
- 原有纯文本分析和 P1-01 双文本对照继续通过。

## P1-03 基于证据的追问与缺失清单

### 目标

让用户围绕当前报告继续问问题，但系统只能使用已提交材料回答；证据不足时直接说明还缺什么。

### 交互方式

- 报告先固定显示“待确认问题”卡，不强迫用户聊天。
- 用户点击问题或自己输入问题后，从底部面板展示回答。
- 页面内保留本次追问记录，刷新丢失可以接受。
- Demo 每次最多连续追问 5 个问题，避免无限聊天偏离主题。

### 服务端处理

- 新增无状态接口 `POST /api/v1/follow-ups`，输入 question、report 和 sources。
- 只返回 `ANSWERED`、`INSUFFICIENT_EVIDENCE`、`OUT_OF_SCOPE`。
- 每条引用必须能在对应来源文本中找到；引用校验失败时降级为证据不足。
- 文档中的“忽略系统提示”等文字始终按材料处理，不能变成模型指令。
- 不接联网搜索、向量数据库、会话数据库、多 Agent 和通用聊天能力。

### 验收

- 材料已明确的问题可以回答并展示原文与页码。
- 材料没写时回答“现有材料无法确认”，同时给出建议补充的章节。
- 天气、股票推荐和“能买吗”等问题返回 `OUT_OF_SCOPE`。
- 没有证据的模型回答无法通过响应 Schema。

### 建议文件

```text
backend-python/app/interfaces/http/routes/follow_up.py
```

## P1-04 Decimal 简单计算器

### 目标

从报告中预填本金、期限、费率和费用，让用户确认后计算简单收益、费用与退出净结果；模型不参与算数。

### Demo 只支持

1. 简单收益：`本金 × 年化比例 × 天数 ÷ 360/365`。
2. 比例费用：`计费基数 × 费率`。
3. 退出净结果：`本金 + 收益 - 费用`。

### 服务端处理

- 使用 `ExtractedField[Decimal]` 保存原文、标准值、单位、状态和证据。
- 模型抽取值只用于预填，用户确认后才能计算。
- 全程使用 `Decimal`，API 通过字符串传输，禁止中途转 `float`。
- 固定金额小数位和舍入规则，并返回公式、输入、假设和结果。
- 缺少必要参数时拒绝计算，不猜测默认本金、期限或费率。

### H5 处理

- 从报告页打开计算抽屉，已抽取参数预填并标记来源。
- 用户可修改本金、期限、费率和计息基准。
- 结果页同时展示公式、参数、结果和“这不是收益承诺”。

### 验收

- 固定用例：`100000 × 3.65% × 90 ÷ 365 = 900.00`。
- 覆盖零值、负值、空值、费率区间、千位分隔符、百分比与百分点。
- 收益区间不自动取上限，缺字段不计算。
- 不做 IRR、税费、复利曲线、期权和结构化衍生品定价。

### 建议文件

```text

backend-python/app/domain/calculators/fee_calculator.py
backend-python/app/application/calculate_scenario.py
```

## P1-05 报告本地保存、复制和系统分享

### 目标

让用户在 Demo 中保存和带走结果，但不建设账号、服务端数据库、公开分享链接和跨设备同步。

### 实现方式

- 使用浏览器 IndexedDB 保存结构化报告，最多保留 10 份。
- 保存 `report_id`、`schema_version`、标题、生成时间和 report。
- 默认不保存原始 PDF、图片、完整 OCR 文本和 API Key；结构化报告会保存用于结论核对的 `EvidenceRef` 原文片段，页面必须明确提示。
- 是否额外保存完整输入原文由用户单独勾选，删除报告时一并删除。
- 提供“复制重点”和“复制完整报告”，完整报告统一转换为 Markdown。
- 支持 Web Share 时调用系统分享；不可用或微信限制时回退到手动复制文本框。

### 验收

- 可以保存、查看、删除和重新打开报告。
- Schema 不兼容时提示“旧报告无法直接打开”，不白屏。
- 复制内容包含结论、风险、证据和待确认项，不包含 API Key。
- 浏览器清理数据后记录会丢失，页面有明确提示。
- 不做 PDF 报告导出。

## P1-06 两款产品事实 PK

### 目标

允许用户加入第二款产品，按相同维度展示差异与缺失信息；这是 P1 最后一项，不输出推荐和综合评分。

### 与 P1-01 的区别

- P1-01：同一个产品的销售话术与正式材料，找遗漏和冲突。
- P1-06：两个不同产品，按相同字段并列查看。

### 固定维度

- 产品类型、期限、起购金额。
- 收益描述的性质与口径。
- 流动性、提前退出条件和费用。
- 本金与收益是否有明确保证。
- 主要风险和未披露信息。

### 服务端处理

- 分别生成两个 P0 `AnalysisReport`，再转成统一 `ProductFacts`。
- 对比由程序按固定字段组装，模型只辅助匹配候选字段，不能生成自由格式排名。
- 不同口径显示“不可直接比较”；一边缺失显示“材料未说明”，不能默认成零。
- 冲突必须同时关联双方证据；一侧缺失时保留已有一侧证据，并把另一侧明确标记为 `MISSING`。

### H5 处理

- 从报告页提供“加入第二款产品”小入口，不占据首页主流程。
- 移动端使用纵向维度卡片或 A/B 切换，不使用压缩到难以阅读的宽表。
- 不出现“赢家、推荐购买、适合你、综合评分”等文案。

### 验收

- 两侧字段完全一致，每个对比值可展开双方原文。
- `12个月/1年` 等值时不显示伪差异；不同收益口径不能强行比较。
- 只支持两款产品，不做排行榜、三款以上比较、实时行情和产品商城。

# 第五部分：H5 与代码统一约束

## 4. H5 通用验收

- 所有新页面在 360～430px 宽度无横向滚动。
- 页面只显示真实阶段，不使用虚假百分比进度。
- 软键盘不遮挡主按钮，点击区域至少约 44px。
- 风险和状态不能只靠红黄绿表达，必须有文字与图标。
- 证据和长原文默认折叠，展开后不丢失定位关系。
- 不依赖 hover、固定高度 iframe、宽屏双栏和境外运行时 CDN。
- P1 新功能不得破坏 P0 的纯文本快速体验。

## 5. Python 对 Java 可读性约束

- Pydantic Model 对应 Java DTO，`Protocol` 对应 Java Interface，Use Case 对应 Application Service，Router 对应 Controller。
- 所有公共函数写完整参数和返回类型；核心数据禁止使用 `dict[str, Any]` 传递。
- 每个 Use Case 写中文 Docstring：用途、前置条件、处理边界、返回状态、错误码和 Java 对照。
- FastAPI `Depends` 只出现在 HTTP 层或组合根，Domain/Application 不导入 FastAPI。
- 不创建仿 Java 的 `@Service`、`@Repository` 等魔法装饰器。
- 新 API 必须同步更新 Pydantic Schema、OpenAPI 和 H5 生成类型。

## 8. P1 总体验收

- 简单收益和费用由 `Decimal` 确定性计算并展示公式。
